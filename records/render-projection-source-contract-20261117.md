# ID14 화면 누락: 카메라와 렌더링을 분리한 새 조사

기준은 v78 C91 ROM이다. 기존 `bizhawk-id14-air-20261117-b`와
`bizhawk-id14-evolution-20261116-c`의 마지막 캡처만 새로 읽었다.
기존 음악·진화·Shoot·전체 자원 검증이나 에뮬레이터를 재실행하지 않았다.

## 좌표 단위와 실제 값

원본 `74239D..7423AD`는 배우의 월드 좌표를 **부호 있는 16비트로 읽어
오른쪽으로 4비트 이동**한 다음 카메라 스냅샷 `3A14/3A16`을 뺀다.
현재 GBA의 `083528DC..08352900`도 `LDRSH → ASR #4 → 카메라 빼기`이며,
리터럴 `083529C4/9C8`은 `0300451C/1E`를 가리킨다.
`08352940..294C`는 결과를 presentation+0/+2 및 배우+3E/+40에 쓴다.
월드 좌표 16단위가 화면 1픽셀이라는 판정은 화면 모양에서 추측한 것이 아니다.

| 실제 캡처 | P1 월드 X/Y | 픽셀 X/Y | 카메라 X/Y | 실제 presentation X/Y |
|---|---|---|---|---|
| 공중 종료 B | 355 / 2118 (`0163/0846`) | 22 / 132 | 0 / 64 | 22 / 68 |
| 지상 종료 C | 355 / 3328 (`0163/0D00`) | 22 / 208 | 0 / 140 | 22 / 68 |

공중 B의 이전 Y는 `0844`다. 현재 `0846`과 모두 픽셀132이므로 이 시점에서
현재/이전 값의 작은 차이가 투영 결과를 바꾸지 않는다. 두 캡처 모두 카메라
스냅샷과 BG0+10/+12가 같고, 별도 지진 보정 조건의 모드2도 아니다.
이는 이 경계에서의 일치이며 모든 프레임의 스냅샷 수명 증명은 아니다.

P1은 두 캡처 모두 화면 안 (22,68)이고 presentation의 숨김 비트0800은 꺼져 있다.
P2의 실제 화면 Y는 B에서352, C에서276이며 숨김 비트0800이 켜져 있다.
따라서 P2가 화면 밖에 있는 것과 P1까지 안 보이는 현상은 구별해야 한다.
이 증거로 카메라 좌표·배율·임계값을 바꿀 근거는 없다.

## 다음 렌더링 수명 관찰

P1의 배우+6에는 큐 등록 비트1000이 있지만 마지막 캡처의 `0300482A` 큐 개수와
`030012CA` OAM 생성 개수는 모두0이다. `03004830`에는 오래된 P1 포인터가 남아
있다. 큐 개수0인 상태에서 잔류 포인터만으로 현재 등록·누락을 단정하지 않는다.
마지막 캡처는 음악 복귀 직후이므로 한 프레임의 전환 화면일 가능성도 남는다.

새 읽기 전용 관찰기 `tools/bizhawk_observe_render_tail.lua`는 부모 실행기가
복귀 경계에서 `frame(0)`을 호출할 때만 활성화된다. 최대 `frame(120)`까지
각 경계의 P1/P2 현재·이전 좌표, 콜백, 플래그, presentation, 이벤트/그림 참조,
카메라 및 생성 개수를 기록한다. 다음 실제 코드 지점도 함께 기록한다.

- `08352998`: presentation 포인터를 큐에 넣는 명령.
- `083734F0`, `0837354C`, `083735BC`: 세 큐 소비자 진입.
- `08012C30`: 스택 인자를 presentation 포인터로 읽은 뒤 렌더러 선택.
- `03000200`, `03000358`: 실제 IWRAM 그림 생성 진입과 생성 개수 저장.

각 명령은 예상 opcode가 다르면 중단한다. IWRAM 코드는 초기 부팅 시 아직
복사되지 않았을 수 있어 실제 활성화 후 실행 지점에서 검사한다. 한 종류당
프레임별8행까지만 내보내고, 전체 호출 수와 생략 수를 별도로 보존한다.
게임 메모리·입력·ROM을 쓰는 API는 없다. 정상 실행의 뒤120프레임을 관찰하는
것은 이 경로의 일시적/지속적 표시 누락을 구별하며 모든 진화 경로를 증명하지 않는다.

## 새 뒤120프레임 관찰: 사라진 화면은 진화 종료 깜박임

부모 실행기의 새 비공개 실행 `build/bizhawk-id14-render-tail-20261117-a`는
지상 진화 종료 뒤 입력을 중립으로 유지했다. 해당 실행의121개 경계에서 P1
월드좌표 `0163/0D00`, 카메라 `0/140`, presentation `(22,68)`는 일정하다.
따라서 보였다가 사라지는 차이를 이 수명에서 카메라 이동으로 설명할 수 없다.

실제 원인은 보존된 깜박임 코드와 일치한다.

1. 진화 종료의 `0835A710..A72C`는 배우+8에 `1001`을 켜고 배우+6F/+72/+73을
   60으로 초기화한다. 원본 `7676B2..76BF`도 같은 플래그와 대응 카운터를
   설정하되 값은75다. 이 조사에서 두 기종의 실제 시간 동등성을 새로 시험한 것은 아니다.
2. `08352ED0..2F20`은 +8의1000이 켜진 동안 +72를 한 번 감소시키고,
   남은 값의 하위2비트가3일 때 +4의20을 반전한다. 0이 되면1000과20을 모두 지운다.
   원본 `743508..352A`는 +5E 카운터로 같은 조건·반전·최종 해제를 수행한다.
3. 실제 큐 소비자 `08373604..361C`는 presentation-0xA8, 즉 배우+4의20이
   켜졌으면 그 배우의 렌더러 호출을 건너뛴다.
4. 첫 관찰 경계의 실제 +72와+6F는58이며, 1·2·4·8·16·32 경계에서
   57·56·54·50·42·26, 64·120 경계에서0이다. 121개 경계의 숨김 플래그가
   위 알고리즘과 모두 일치한다. 나이58부터120까지20이 꺼진 채 유지된다.
5. 다음 프레임에서 숨김이 해제될 때만 실제 dispatch가 호출되어 총91회다.
   P2는 이 동안 화면 아래에 있으므로 P1의 깜박임 프레임에는 둘 다 보이지 않는다.

새 `tools/check_render_blink_tail.py`는 원본/현재 opcode,121개 상태,9개 실제 RAM의
카운터와 P1 자원,91회 dispatch,6개의 직접 의미 변이 거부를 새로 확인했다.
`build/render-tail-observer-20261117/blink-source-tail.json` 결과는
`RENDER_BLINK_SOURCE_AND_TAIL_PASS`, SHA-256
`C34DFFF221B21251612E9CBA7B1EA1D538F5B9E2DB490E4E25E0BC49DAABE835`다.

### 관찰 지점의 한계도 확인함

두 IWRAM 렌더러 후크의 호출은0이다. 실제 선택 표 `08012C50`은 현재
`086FF240`을 가리키고, P1의 tile base1은 그곳에서 기존 대체 렌더러
`086FEA00`으로 간다. 따라서 IWRAM 후크0은 렌더링이 실행되지 않았다는
증거가 아니며 이 조사에서 그 후크로 내부 타일 복사를 관찰했다고 주장하지 않는다.
실제 dispatch91회와 새 OAM·화면의 재출현은 별도 증거다.

이 정상 깜박임을 없애는 플래그/카메라 수정은 하지 않았다. 이 한 지상 경로에서의
지속적 표시 누락은 반증됐으며, 다른 카메라 경로 전체나 E5 해결을 판정한 것은 아니다.
원본 ROM, 메인 빌더, Git은 바꾸지 않았다.
